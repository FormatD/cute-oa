# P1-F4 费用预算与采购付款闭环任务书

## 1. 文档目的

本文档用于指导后续 worker 完成 P1-F4“费用预算与采购付款闭环”的整改、补全和独立验收。产品规则以 [28-费用预算与采购付款闭环 PRD](./28-费用预算与采购付款闭环PRD.md) 为基线；本文档负责描述当前代码边界、阻塞问题、工作包、合并顺序和验收证据。

- 复查基线：`main@279a5ba`
- 复查日期：2026-09-07
- 当前结论：已有可运行首版，但尚未达到 P1-F4 验收和生产候选标准。
- 本轮范围：费用发票、预算、报销付款、采购付款、采购四单对账、财务导出及相关权限和测试。
- 暂不纳入：P0-F3 独立复查中已记录但经项目负责人决定暂缓的历史配置迁移、采购损坏快照失败关闭和真实 MFA E2E 问题。

## 2. 已有能力与保留边界

以下能力已经存在，后续实现不得无故回退：

- 已建立 `budget`、`budget_transaction`、`expense_invoice`、`payment_transaction` 表及迁移；
- 报销支持结构化发票要素、发票指纹、提交查重、撤回/驳回释放和付款归档；
- 报销和采购提交可关联预算池，驳回/撤回可释放，付款可结转实际支出；
- 报销和采购均支持多笔付款流水、付款状态和流水号防重；
- 采购详情已有申请额、下单额、验收额、已付额和待付敞口展示；
- 已有报销与采购 CSV 导出、付款审计和 PostgreSQL 正常路径测试；
- 报销和采购表单可展示当前部门预算水位；
- 现有构建、领域测试、PostgreSQL 集成测试和 Playwright 基础回归已通过。

这些能力证明数据模型和主要页面已经起步，但现有测试主要覆盖串行正常路径，不能证明权限隔离、并发资金安全和完整预算语义。

## 3. 阻塞验收的问题

### 3.1 P0：付款流水查询存在业务数据权限旁路

`PaymentService.GetPayments` 直接按调用方传入的 `businessType` 和 `businessId` 查询付款流水，没有先验证调用方是否有权查看对应报销单或采购单。普通登录用户只要获得或猜到业务 ID，就可能读取不属于自己的付款日期、付款账户、收款人、开户行、银行流水号、金额和经办人。

整改要求：

1. 只接受明确枚举的 `Expense`、`Purchase`，未知类型返回 400；
2. 查询流水前调用对应业务服务的数据范围规则，申请人、当前审批人、合法抄送人和授权财务仅能看到其应见单据；
3. 非财务用户仅返回脱敏收款账号，不返回企业付款账号、完整银行流水号等非必要字段；
4. 付款凭证下载继续走文件关联权限，不因知道附件 ID 即可下载；
5. 增加本人、直属下级、无关员工、财务、采购管理员五类 PostgreSQL 权限用例。

### 3.2 P0：预算查询可通过筛选参数绕过数据范围

`BudgetService.List` 在传入 `departmentId` 时直接按该部门查询，跳过非全局用户的数据范围限制；`Check` 也允许任意部门预算预检。`GetTransactions` 未验证调用方是否能查看目标预算池。预算金额、执行额和关联业务流水因此可能跨部门泄露。

整改要求：

1. 先计算调用方可见部门集合，再应用客户端筛选条件；筛选条件只能缩小权限范围，不能扩大范围；
2. 部门负责人按真实管理链查看下级部门，普通员工仅能查看本人申请需要的最小预算摘要；
3. 预算详情和流水接口统一复用同一数据范围判定；
4. 预算预检不得泄露无权查看部门的编制额、占用额和实支额；
5. 全公司财务权限只作用于预算、费用和采购，不外溢到人事或合同。

### 3.3 P0：付款、预算和发票防重缺少数据库并发保证

当前付款先读取 `PaidTotalAmount` 再写入，付款序号使用 `Count + 1`；预算预占/释放/结转也是先读余额再更新；发票防重只做业务层查询，数据库索引不是活动发票唯一约束。两个独立请求同时执行时，可能产生超额付款、重复付款序号、预算超占、余额覆盖或同一发票同时被两张单据占用。

整改要求：

1. 报销和采购付款在事务内锁定目标业务单据，锁内重新计算累计付款和本次上限；
2. 为同一业务单据的付款序号增加数据库唯一约束，冲突转换为可重试的 409；
3. 预算余额变更使用 PostgreSQL 行锁或等价原子更新，并保留乐观并发版本；
4. 为活动发票建立可执行的数据库唯一方案。可使用活动占用表或 PostgreSQL 部分唯一索引，不能依赖“先查后写”；
5. 数据库唯一冲突必须返回稳定业务错误，不能暴露 500；
6. PostgreSQL 测试必须使用两个独立 DbContext/连接和同步起跑点。

### 3.4 P0：预算流水可重复释放或重复结转

`Release` 和 `Consume` 依据调用方传入金额直接修改汇总值，缺少业务动作唯一键和剩余可释放/可结转金额校验。重复调用会重复生成流水；`Math.Max(0, ...)` 只能隐藏负数，不能保证账本正确。旧的单笔付款入口与新的多笔付款入口并存，也会形成两套结转路径。

整改要求：

1. 预算流水增加业务动作幂等键或唯一约束，例如业务类型、业务 ID、动作类型、付款流水 ID；
2. 释放金额不得超过该业务当前未释放预占，结转金额不得超过当前未结转预占；
3. 每笔付款与一笔 `CONSUMED` 流水一一对应，重复请求只返回原结果；
4. 汇总金额必须可由不可变流水重算并与预算池字段一致；
5. 移除或明确废弃 `/expense-claims/{id}/payment` 旧入口，统一使用多笔付款模型。

### 3.5 P1：预算维度没有真正驱动报销和采购

PRD 定义了部门、费用科目、项目、年度/月度维度，但报销和采购提交均以 `expenseCategory = null` 查找预算池，`ProjectId` 也没有进入匹配逻辑。业务单据保存的是部门名称，而预算示例同时出现部门编码和名称，容易导致配置了预算却匹配不到。

整改要求：

1. 统一使用稳定 `DepartmentId`，名称只用于显示；
2. 报销按费用明细科目分摊预占，不能把多科目单据全部压入部门通用池；
3. 采购保存并使用采购科目/预算科目映射；项目预算启用时保存 `ProjectId`；
4. 明确月度预算优先于年度预算、科目预算优先于部门通用预算的匹配顺序；
5. 单据快照保存命中的预算池和各池占用明细，以支持准确释放和分笔结转；
6. 明确“未配置预算池”的租户策略，不得用 `9,999,999` 伪造可用额度。

### 3.6 P1：预算生命周期和管理页面未完成

领域模型声明了 Draft、Active、Frozen、Closed，但创建预算时直接写入 Active，后端没有发布、冻结、关闭和恢复规则；前端只有 API 封装和业务表单中的水位卡片，没有预算列表、详情、流水和调整页面。预算列表也未服务端分页。

整改要求：

1. 落实 Draft → Active → Frozen/Closed 状态机及允许操作；
2. 发布、冻结、关闭和额度调整均使用并发版本、幂等和审计；
3. 新增预算中心路由、权限菜单、分页列表、筛选、详情、流水和调整弹窗；
4. 列表服务端分页并按 `UpdatedAt`、`Id` 稳定倒序；
5. 390px 宽度下页面可操作，表格只在容器内横向滚动；
6. 不具备预算管理权限的用户不能看到维护入口。

### 3.7 P1：超预算软控制没有形成特批流程

当前非阻断策略仅允许预算变为负可用额度并显示提示，单据没有保存超预算金额、命中策略和特批状态，流程中也没有自动加入财务经理/总经理节点。因此“允许超预算并触发特批”尚未闭环。

整改要求：

1. 单据保存预算检查结果、超额金额、策略版本和特批状态；
2. 阻断策略在事务内严格拒绝，非阻断策略必须进入明确的财务特批节点；
3. 审批详情展示预算池、提交时余额、预占额和超额原因；
4. 驳回、撤回、重新提交、金额修改和流程重走均正确释放并重新预占；
5. 超预算路由使用提交时快照，后续策略变更不改写历史单据。

### 3.8 P1：导出和财务台账契约不完整

报销和采购导出虽然接收 `startDate`、`endDate`，实现中没有应用日期筛选；导出直接一次性加载全部结果，缺少导出上限或异步任务边界。发票台账和付款流水也没有形成统一的财务分页页面。

整改要求：

1. 所有筛选参数必须真实生效，并在审计中记录筛选条件和行数；
2. 设置同步导出行数上限，超过上限返回明确提示并预留异步导出任务接口；
3. CSV 防公式注入，对以 `= + - @` 开头的文本做安全转义；
4. 建立分页发票台账和付款台账，默认最新记录在前；
5. 导出与台账复用同一权限过滤，不允许导出接口成为数据范围旁路。

### 3.9 P1：缺少浏览器全链路验收

当前 Playwright 用例未覆盖 P1-F4。现有 PostgreSQL 用例只验证单连接串行正常路径，没有覆盖权限旁路、并发竞争、预算生命周期、超预算特批、筛选导出和移动端财务操作。

必须补充以下核心链路：

1. 财务创建并发布预算，员工表单看到正确水位；
2. 员工提交带附件的结构化发票，重复发票被阻断；
3. 预算正常预占、驳回释放、重提再预占、分笔付款结转；
4. 采购下单、预付款限制、验收、尾款和四单对账；
5. 无关员工不能读取预算流水、付款流水和付款凭证；
6. 390px 视口完成预算查询、报销发票录入和财务付款。

## 4. 推荐工作包

### WP-A：财务权限与敏感数据保护

优先级：P0，最先合并。

主要范围：

- 统一敏感账户、流水号和付款凭证的字段级返回策略；
- 收紧采购付款权限，落实财务与采购职责分离；
- 增加越权、横向访问和附件下载测试。

主要文件：

- `backend/Oa.Api/Services/PaymentService.cs`
- `backend/Oa.Api/Services/BudgetService.cs`
- `backend/Oa.Api/Services/ExpenseService.cs`
- `backend/Oa.Api/Services/PurchaseService.cs`
- `backend/Oa.Api/Program.cs`
- `tests/Oa.Postgres.Tests/Program.cs`

### WP-B：资金并发、幂等与账本一致性

优先级：P0，在 WP-A 后合并。

主要范围：

- 付款单据行锁、付款序号唯一、超付并发保护；
- 预算预占、释放、结转原子化和动作幂等；
- 活动发票数据库级唯一占用；
- 预算汇总与流水重算校验；
- 合并或废弃旧付款入口。

数据库迁移必须由一个 worker 统一生成。后续 worker 基于最新 `main` 继续，不得手工合并两个不一致的 ModelSnapshot。

### WP-C：预算领域闭环和管理页面

优先级：P1，在 WP-B 数据语义稳定后合并。

主要范围：

- 稳定部门 ID、费用科目、项目、月度/年度预算匹配；
- 多预算池预占明细模型；
- 预算状态机、发布/冻结/关闭/调整；
- 预算中心分页列表、详情、流水、权限菜单和移动端；
- 报销、采购表单使用后端预算预检结果，不自行选择 `list[0]`。

### WP-D：超预算特批、财务台账和导出

优先级：P1，在 WP-C 后合并。

主要范围：

- 超预算策略快照、特批节点、详情展示和重提语义；
- 发票台账、付款台账和采购对账查询页面；
- 导出筛选、数据范围、行数上限、CSV 安全和审计；
- 付款回单必填规则和附件关联权限。

### WP-E：全链路验收与文档收口

优先级：P1，最后合并。

主要范围：

- 增加两个独立数据库连接的并发测试；
- 增加 P1-F4 浏览器全链路和 390px 用例；
- 回填 PRD、API、数据库和运行手册；
- 独立 review，不由实现 worker 自行宣布完成。

## 5. 合并顺序与 worker 流程

推荐顺序：`WP-A → WP-B → WP-C → WP-D → WP-E`。

每个 worker 必须：

1. 从最新 `main` 创建 `codex/p1-f4-wp-<letter>` 分支；
2. 开始前阅读本文档和 28 号 PRD，只认领一个工作包；
3. 先增加可以稳定暴露问题的失败测试，再实现修复；
4. 写操作统一使用幂等键和并发版本，资金相关变更必须在同一数据库事务内完成；
5. 每个提交只覆盖一个可审查主题，提交标题包含工作包编号；
6. 更新本文档第 7 节证据，不删除未完成问题；
7. 推送分支后交由独立 worker 审查，再按顺序合并。

建议提交标题：

- `fix(p1-f4-wp-a): enforce finance data scopes and masking`
- `fix(p1-f4-wp-b): make budget and payment ledgers atomic`
- `feat(p1-f4-wp-c): complete budget lifecycle and management ui`
- `feat(p1-f4-wp-d): close over-budget approval and finance reporting`
- `test(p1-f4-wp-e): add finance closure acceptance suite`

## 6. 验收门禁

每个工作包执行相关定向测试；最终必须全部通过：

```bash
bash scripts/verify.sh
bash scripts/verify-postgres.sh
npm run test:e2e --prefix frontend
git diff --check
git status --short --branch
```

最终验收还必须证明：

- 无关用户无法读取预算、发票、付款流水、银行账户和付款凭证；
- 两个并发付款请求不会超付，两个并发预算请求不会超占；
- 同一活动发票在并发提交时至多一个成功；
- 预算流水可重算汇总余额，重复释放/结转不会改变余额；
- 部门、科目、项目和月份维度都能改变真实匹配结果；
- 超预算阻断和特批两条路径均形成可追溯快照；
- 所有列表服务端分页并稳定倒序；
- 财务导出的筛选、权限、审计和 CSV 安全均有测试；
- 桌面和 390px Web 端均能完成核心链路。
