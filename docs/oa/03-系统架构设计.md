# OA V1.0 系统架构设计

## 1. 架构原则

- 模块化单体优先：先保证交付速度和事务一致性，按领域划分代码边界，未来可独立拆分。
- 配置优先：表单、流程、字典、通知模板和权限尽量配置化。
- 统一业务底座：所有业务复用租户、用户、组织、文件、流程、消息、审计和字典。
- API 优先：前端、移动端和第三方集成使用同一套版本化 API。
- 可审计：关键数据变化记录操作者、时间、前后值、请求标识和来源。

## 2. 分层结构

```text
Web / 移动端 / 企业微信钉钉
          ↓
API 网关：认证、限流、幂等、版本、审计上下文
          ↓
应用层：工作台、流程、表单、请假、报销、采购、合同、知识、任务
          ↓
领域层：状态机、权限判定、金额路由、工作日计算、编号生成
          ↓
基础设施：PostgreSQL、Redis、对象存储、消息队列、全文搜索
          ↓
外部系统：身份、消息、财务/ERP/CRM、电子签
```

## 3. 核心模块边界

| 模块 | 负责 | 不负责 |
|---|---|---|
| 身份与租户 | 持久化账号、密码校验、登录锁定、短期 JWT、刷新令牌轮换、会话查看/撤销、租户上下文 | 外部身份源、MFA 和统一登录 |
| 组织权限 | 用户、部门树、岗位、经理关系、角色、操作权限、请假/报销角色数据范围 | 业务审批规则本身 |
| 流程引擎 | 实例、节点、任务、路由、审批轨迹 | 业务单据字段和财务记账 |
| 表单中心 | 字段定义、校验、版本、渲染元数据 | 复杂领域计算 |
| 业务模块 | 单据、业务规则、状态和领域数据 | 通用审批任务实现 |
| 文件中心 | 上传、元数据、权限、版本、病毒校验 | 文件内容业务解释 |
| 消息中心 | 模板、站内信、渠道、重试、已读 | 即时聊天 |
| 数据中心 | 聚合指标、报表和导出 | 原始业务数据维护 |

## 4. 非功能基线

以下为 V1.0 初始目标，正式立项时按企业规模校准：

- 普通读写接口 P95 ≤ 500ms；导出、全文搜索和报表接口异步化。
- 列表默认 20 条、最大单页 100 条；大数据量必须分页。
- 支持 500 个并发在线用户，关键流程提交具备幂等保护。
- 关键服务可用性目标 99.9%；数据库每日备份，至少保留 30 天。
- 密码不可逆加密存储；敏感字段脱敏展示；文件按租户和业务权限校验。
- 支持 Chrome、Edge 最近两个稳定大版本；移动端优先保证审批和查询。

## 5. 一致性与可靠性

- 单据提交、流程实例创建、首个任务创建在同一事务内完成。
- 通知发送采用事务事件/消息表，业务事务成功后异步投递，失败可重试。
- 所有写接口支持 `Idempotency-Key` 或业务唯一键，重复提交返回原结果。相同租户、操作者、路由和键先通过 PostgreSQL advisory lock 跨实例串行化；人事、组织、用户、考勤和劳动合同写操作将业务变更与成功响应记录放在同一数据库事务中，避免“业务已提交、幂等记录未写入”的崩溃窗口。
- 外部系统调用记录请求、响应摘要、重试次数和最终状态，不阻塞核心单据落库。
- 删除采用业务软删除；文件进入回收站，超过保留期才允许物理清理。

## 6. Web 前端模块边界

Vue 前端采用“领域 API + 领域 Pinia Store + 工作区协调层”的结构：

```text
views / components
        ↓
领域 Store（页面优先直接依赖）
        ↓
app（跨模块动作门面） / workspace（初始化、刷新、清理） / detail（详情编排） / files（附件）
        ↓
auth / security / identity / department-admin / position-admin / announcements / leave / expense / travel / workflow / organization / workspace / ui
        ↓
api/client.ts（共享鉴权客户端） / api/modules（领域接口）
        ↓
api/http.ts（鉴权、幂等、错误处理、附件传输）
```

- 页面状态和业务操作按认证、请假、报销、流程、组织、工作台拆分，禁止重新集中到单个工作区文件。
- `stores/workspace.ts` 只负责应用启动后的公共数据加载、跨业务刷新和退出清理；`stores/app.ts` 不持有业务状态，只兼容现有页面的登录及跨模块动作编排；`detail.ts` 与 `files.ts` 分别封装详情加载和附件传输。
- 页面直接依赖对应领域 Store，不再通过聚合式工作区门面访问全部状态；领域状态和操作不得回流到 `workspace.ts` 或 `app.ts`。
- API 端点按业务模块维护，共享 HTTP 层统一附加 JWT、`Idempotency-Key`、携带 HttpOnly Cookie，并在 401 时单次刷新后重放原幂等请求。
- `api/modules` 保持与 Pinia 无关；`api/client.ts` 是唯一绑定认证 Store 的适配层，所有业务 Store 复用同一鉴权客户端，禁止重复创建 HTTP 客户端。

## 7. 当前身份安全实现

- 用户、账号、部门树、角色、用户角色和角色权限均写入 PostgreSQL；应用启动只补齐缺失的演示基线，不清空或覆盖管理员后续创建的数据。
- 密码使用随机盐和 PBKDF2-SHA256（当前 120,000 次）不可逆保存；管理员可重置密码，但接口和日志不返回密码或哈希。
- 连续 5 次密码错误后账号锁定 15 分钟；管理员重置密码时清除失败次数和锁定状态。
- 访问令牌默认 15 分钟，仅驻前端内存；30 天刷新令牌通过 SameSite=Lax、HttpOnly Cookie 传输，数据库只保存 SHA-256 摘要并在每次刷新时轮换。
- 每个 JWT 包含会话 ID；受保护请求同时验证数据库中的 ACTIVE 用户和未撤销、未过期会话。退出、重置密码、停用账号或安全角色变化会使对应既有访问令牌立即失效。
- 用户可查看按最近使用时间倒序分页的登录设备，并撤销单个其他会话或全部其他会话；当前会话只能通过退出登录撤销。
- 页面路由和菜单仅用于改善体验，`USER_MANAGE`、`ORG_MANAGE`、`PROCESS_MANAGE`、`AUDIT_VIEW`、`CALENDAR_MANAGE`、`EXPENSE_PAY`、`LEAVE_SCOPE_VIEW`、`EXPENSE_SCOPE_VIEW` 和兼容权限 `EXPENSE_ALL_VIEW` 均在服务端再次校验。
