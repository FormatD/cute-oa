# P0-F3 业务参数配置中心整改任务书

## 1. 文档目的

本文档用于把 P0-F3 业务参数配置中心的复查问题交接给后续开发 worker。后续实现以 [27-业务参数配置中心 PRD](./27-业务参数配置中心PRD.md) 为需求基线，以本文档为整改范围、实施顺序和验收门禁。

初始复查基线：`main@46f8306`；第一次整改分支独立复验基线：`main@25dab19` + `origin/codex/p0-f3-rectification@d36d420`；复查日期：2026-09-06。

当前结论：配置中心的数据模型、管理 API、管理页面、版本快照和基础自动化已经存在，但状态机、并发排他、部分安全门禁以及六个业务域的规则执行尚未完整闭环。P0-F3 状态应为“整改复验中”，不得仅凭管理端正常路径测试将其标记为完成或发布候选。

## 2. 已完成且应保留的能力

- PostgreSQL 已建立业务配置记录及五类业务单据的配置版本、版本号、JSON 快照和解析时间字段；
- 已建立 `BUSINESS_CONFIG_MANAGE` 权限、配置列表/详情/草稿/升版/发布/下线/删除 API；
- 已具备 Draft、Scheduled、Effective、Retired 状态展示和基础时间区间检查；
- 已具备结构化表单、原始 JSON、历史版本、引用计数和基础审计；
- 请假、报销、差旅、采购、用章在创建或提交时已能保存配置快照；
- 完整构建、领域测试、PostgreSQL 集成测试和现有 5 条 Playwright 用例在复查基线上通过。

上述能力是整改起点，不应在后续修改中被回退。

## 3. 阻塞 P0-F3 验收的问题

### 3.1 P0：已发布版本仍可被改写

`BusinessConfigurationService.Publish` 没有限制记录必须为 Draft。Effective、Scheduled 或 Retired 版本可以再次调用发布接口并原地修改状态、生效区间和发布元数据；`Retire` 也没有限制来源状态，草稿可能被直接下线。

目标状态机必须固定为：

| 当前状态 | 允许操作 | 目标状态 |
|---|---|---|
| Draft | 编辑、删除、发布 | Draft / Scheduled / Effective |
| Scheduled | 到期自动生效、管理员取消/下线 | Effective / Retired |
| Effective | 管理员下线、被新版本替代 | Retired |
| Retired | 查看、基于此版本创建新草稿 | Retired |

Published 版本包括 Scheduled、Effective、Retired。Published 版本的内容、生效起始时间和版本号必须不可原地修改。

### 3.2 P0：配置字段没有完整驱动业务行为

| 业务域 | 已接入 | 待整改 |
|---|---|---|
| Leave | 假别启停、最小单位、附件门槛、年假上浮 | `allowCrossYear`、`compTimeValidityDays` 未执行；默认配置含婚假/产假/陪产假/丧假，但业务枚举和表单不支持 |
| Expense | 提交时的类别启停、单项限额、超限说明 | 创建/编辑仍使用固定类别并强制每条明细上传附件，新增类别和 `requiresReceipt=false` 无效 |
| Travel | 配置版本和 JSON 快照 | 城市等级、员工职级、住宿限额、餐补和交通标准均未参与校验或提示 |
| Procurement | 报价附件起计金额 | 配置类别、金额档位、默认采购负责人、是否强制验收、验收负责人未执行 |
| Seal | 印章启停、是否允许外带、文件类别风险等级 | 印章/文件类别仍受固定集合限制；最长外带天数、保管人、风险路由指标未执行 |
| Dictionary | 配置管理和版本发布 | 公告类型、合同类型、附件类型、常用审批意见没有被对应业务页面/API 消费 |

### 3.3 P1：生效切换与并发排他不可靠

- `GET /effective` 当前会修改数据库状态，不是只读查询；
- 到期 Scheduled 记录没有独立后台生效机制，业务解析和管理页面状态可能不一致；
- 多条到期记录没有稳定排序和同配置编码级互斥；
- 发布时仅在应用层先查询再保存，数据库没有时间区间排他约束；
- 同一 Domain + Code 并发创建新版本时采用 `max(version) + 1`，存在版本号冲突窗口。

### 3.4 P1：敏感权限没有完整安全门禁

`BUSINESS_CONFIG_MANAGE` 已存在，但未加入 MFA 必须权限清单。只持有该权限的自定义角色可以在不触发 MFA 的情况下发布全公司业务规则。

### 3.5 P1：测试和文档完成度高于实际实现

新增 Playwright 用例只验证管理员查看详情、UI/JSON 切换、创建草稿、立即发布和升版的正常路径，尚未证明配置变化会改变业务行为，也没有覆盖重复发布、并发发布、定时生效、历史快照不可变、MFA 和配置中心移动端。

PRD/API 仍存在以下契约差异：

- PRD 使用 `/{id}/branch` 和 `/{id}/history`，实现使用 `/{id}/versions`；
- PRD 的列表/详情权限写为登录用户，实现要求 `BUSINESS_CONFIG_MANAGE`；
- PRD 描述 `date` 和 PostgreSQL `xmin`，实现使用 `DateTimeOffset` 和手工 `ConcurrencyVersion`。

### 3.6 P2：前端可维护性债务

`BusinessConfigurationPage.vue` 超过 3200 行，领域表单、详情、版本、发布、筛选和弹窗逻辑集中在单文件中。当前可以运行，但不利于后续六个业务域继续演进，并使回归影响范围过大。

## 4. 推荐工作包与认领边界

后续 worker 应优先认领一个工作包，避免多人同时修改相同核心文件。若一个 worker 需要跨工作包修改，必须在提交说明中列出原因和影响。

### WP-A：配置状态机、定时生效与并发排他

优先级：P0，必须最先合并。

主要文件：

- `backend/Oa.Api/Services/BusinessConfigurationService.cs`
- `backend/Oa.Api/Services/BusinessConfigurationDefaults.cs`
- `backend/Oa.Api/Services/BusinessConfigurationEndpoints.cs`
- `backend/Oa.Api/Persistence/OaDbContext.cs`
- `backend/Oa.Api/Persistence/Migrations/`
- `tests/Oa.Domain.Tests/Program.cs`
- `tests/Oa.Postgres.Tests/Program.cs`

工作内容：

1. 发布接口只接受 Draft；重复发布、复活 Retired、改写 Scheduled/Effective 必须返回 `CONFIG_002` 或明确的新错误码；
2. 下线接口只接受 Scheduled 或 Effective，并验证 `EffectiveTo >= EffectiveFrom`；立即下线由服务端确定时间，不能生成倒置区间；
3. 将 `GET /effective` 改为纯查询，不在 GET 中执行状态写入；
4. 增加定时生效后台任务，或采用统一的派生状态方案。无论选择哪种方案，管理列表、有效配置查询和业务解析必须使用相同口径；
5. 对同一 TenantId + Domain + Code 的发布和升版分配增加数据库级互斥。优先考虑 PostgreSQL 事务级 advisory lock 或排他区间约束，并对唯一冲突返回可理解的 409；
6. 确保同时发布两个重叠草稿时至多一个成功；同时创建两个新版本时版本号不重复且调用方收到可重试结果；
7. 移除配置解析中的宽泛异常吞噬。生产环境无法读取配置时必须失败关闭并留下可观测日志，不能静默回退到代码默认值。

验收用例：

- Draft 可发布，Effective/Scheduled/Retired 再发布均失败；
- Draft 不可下线，Scheduled/Effective 可下线，Retired 重复下线失败；
- 两个并发请求发布重叠区间，只有一个提交成功；
- 两个并发升版请求不会产生未处理的 500；
- Scheduled 到期后按确定顺序切换；查询接口不产生 UPDATE SQL；
- 旧版本被替代后不再匹配新单据，但历史单据引用和快照不变。

### WP-B：六个业务域规则执行闭环

优先级：P0；在 WP-A 合并后开发，可按业务域拆给多个 worker，但每个 worker 必须同时补测试。

#### WP-B1：请假

1. 扩展后端枚举、API 序列化、前端选项和显示映射，支持配置默认提供的婚假、产假、陪产假和丧假；
2. `allowCrossYear` 必须实际控制跨自然年度申请；关闭时拒绝，开启时按明确规则拆分或冻结余额；
3. `compTimeValidityDays` 必须有可计算的数据来源。若当前余额模型无法表达调休获得日期和过期时间，增加调休余额明细/到期模型及迁移，不得只保留无效配置字段；
4. 保持中国法定年假最低标准，企业上浮只能增加不能降低；年假余额应固定年度计算依据，避免年中配置变化无审计地改写已产生余额。

#### WP-B2：报销

1. 创建、编辑、提交使用同一份生效费用策略；
2. 可用类别完全来自配置，停用类别不能新建或提交；
3. `requiresReceipt`、单项限额、超限说明和阻断策略在服务端统一执行；
4. 前端类别和票据提示从有效配置获取，不能维护另一份固定列表；
5. 与 P1-F4 发票防重逻辑兼容，不得弱化已有重复发票门禁。

#### WP-B3：差旅

1. 明确员工职级的数据来源。建议为差旅策略增加稳定的职级编码与岗位/角色映射，普通员工为默认档，部门负责人和总经理由组织/角色映射；
2. 根据目的地解析城市等级，根据申请人解析职级，匹配唯一差旅标准；
3. 对住宿、餐补和交通标准提供服务端校验或明确的超标提示/原因机制；若申请模型缺少实际字段，先补齐模型、迁移、API 和表单；
4. 提交时冻结实际命中的城市等级、职级和标准，审批详情可查看。

#### WP-B4：采购

1. 采购类别来自有效配置；
2. 金额档位必须参与审批路由或形成明确的业务分级结果，不能仅展示；
3. 默认采购负责人应在审批完成后的采购执行环节自动指派；
4. `requiresAcceptance=false` 时允许按规则跳过验收，开启时必须完成验收后才能进入付款；
5. `acceptanceRoleOrAssignee` 必须解析为有效人员/角色，并执行数据范围校验；
6. 保持 P1-F4 的预算、订单、验收、发票和多笔付款闭环不回退。

#### WP-B5：用章

1. 可用印章和文件类别来自配置，不再由静态集合决定；
2. 外带起止日期必须受对应印章 `maxOutDays` 限制；
3. 印章保管人参与执行权限或任务指派；
4. 路由指标使用配置的 Low/Medium/High 风险参数，不再使用固定 1/2/3；
5. 审批详情展示命中的印章、保管人、文件风险和外带规则快照。

#### WP-B6：系统字典

1. 公告新增/编辑表单读取 AnnouncementType；
2. 劳动合同类型读取 ContractType，同时保留固定期限、无固定期限、项目期限的法定业务校验；
3. 上传附件或附件表单读取 AttachmentType，并保存稳定字典编码；
4. 审批意见输入框提供 ApprovalCommentPreset 快捷选择，仍允许手工输入；
5. 已停用字典项不能用于新数据，历史数据继续显示保存时名称或快照；
6. 为各字典提供受权限控制的有效项查询 API，业务页面不得请求配置管理详情接口。

各业务域通用验收：

- 发布 v1 后，新单据按 v1 行为校验并保存 v1 快照；
- 发布 v2 后，历史单据仍显示 v1，新单据按 v2；
- 驳回单据重新提交时重新解析并冻结 v2；
- 停用类别/字典项不会影响历史展示，但不能用于新单据；
- 缺少匹配规则、规则 JSON 损坏或配置读取失败时返回明确业务错误，不静默使用旧代码常量。

### WP-C：MFA、安全、API 与文档契约

优先级：P1，可与 WP-B 并行，但最终应在 WP-D 前合并。

主要工作：

1. 将 `BUSINESS_CONFIG_MANAGE` 加入默认及部署配置中的 MFA 必须权限；
2. 增加“只持有业务配置管理权限”的角色登录测试，确认触发 MFA；
3. 确认配置列表和详情的预期权限。推荐仅配置管理员查看完整 JSON，业务用户通过独立有效项/规则摘要 API 获取必要数据；
4. 统一 PRD、API 文档和实现中的 `branch/history/versions` 路径；
5. 统一日期边界、时区和并发字段说明；所有生效判断使用中国业务日期或文档明确的 UTC 时间点，不得混用；
6. 审计创建、编辑、升版、发布、下线、删除及关键失败。失败审计不能因业务事务回滚而一并消失；
7. 更新生产运行手册中的敏感权限和配置发布审计检查项。

## 5. 实施与合并流程

### 5.1 开始工作

1. 阅读 `docs/oa/27-业务参数配置中心PRD.md` 和本文档；
2. 从最新 `main` 创建 `codex/p0-f3-<work-package>` 分支；
3. 在开始修改前记录工作区状态，保留其他 worker 已有改动；
4. 只修改当前工作包必要文件，不在项目目录外写入业务文件；
5. 若发现需求字段缺少数据来源，先在当前分支补充设计说明，再实现模型和迁移，不得以代码常量代替。

### 5.2 开发循环

1. 先补能复现缺陷的失败测试；
2. 实现最小完整修复；
3. 补充权限、并发、状态边界和历史数据兼容用例；
4. 更新 PRD、API、数据库或运行手册中受影响的内容；
5. 运行当前工作包的定向测试，再运行全量门禁；
6. 提交信息应包含工作包编号，例如 `fix(p0-f3-wp-a): enforce immutable configuration lifecycle`。

### 5.3 推荐合并顺序

1. WP-A：状态机、有效配置解析、迁移与并发；
2. WP-B1 至 WP-B6：按业务域逐个合并，每次合并后重跑 PostgreSQL 回归；
3. WP-C：安全和契约，可提前开发，但应基于 WP-A 最终 API 合并；
4. WP-D：前端整合、完整 E2E 和文档验收；
5. 最后由独立 review worker 按第 6 节重新验收，不由原实现 worker 自行宣布完成。

存在数据库迁移冲突时，后合并 worker 必须基于最新 `main` 重新生成迁移和 ModelSnapshot，不得手工保留两个不一致快照。

## 6. 完成定义与验证命令

所有工作包合并后必须同时满足：

- 六个业务域不是“只保存快照”，而是配置字段能够改变真实业务校验、指派、路由或选项；

- 新单据、历史单据、驳回重提分别遵循正确版本；
- 关键配置管理受权限、MFA、幂等、并发和审计保护；

### 8.3 关键问题的实现约束

#### R-A1：发布与升版并发语义

1. `PublishBusinessConfigurationRequest.ConcurrencyVersion` 和下线请求的并发版本应为必填；缺失或不匹配统一返回 409，而不是使用服务端最新版本继续执行。
2. 获取同租户、同 Domain、同 Code 的事务锁后，必须重新读取目标草稿及重叠版本，并再次校验状态、版本和时间区间。
3. 管理员主动发布计划替代版本时，可以按明确产品语义截断旧 Effective；但两个基于同一旧状态同时发起的请求不得都成功。后取得锁的陈旧请求必须失败，不能被解释为新的主动替代操作。
4. 升版同样在锁内分配版本号；唯一冲突应转换为可重试的 409，不得暴露数据库异常。
5. PostgreSQL 测试必须使用两个 service scope/DbContext 和同步起跑点，不接受把两个调用按顺序执行后称为并发测试。

#### R-A2：配置初始化与读取边界

1. 保留默认配置，但只允许在启动初始化、租户初始化或显式运维命令中幂等写入。
2. `ResolveEffectiveConfig`、业务详情查询和字典显示名解析必须是纯读取，不得因为 GET 或业务查询产生 INSERT/UPDATE。
3. 配置缺失、JSON 损坏、版本区间冲突应输出结构化错误和可观测日志。生产环境不得以 catch-all 后继续使用代码常量掩盖配置故障。
4. 测试应在读取前后比较配置表数据与更新时间，证明查询零副作用。

#### R-B1：业务表单消费有效配置

1. 后端增加面向已登录业务用户的轻量读取接口，只返回当前有效且允许使用的规则/选项；不要复用包含管理元数据和草稿内容的管理详情接口。
2. 前端建立独立 API 目录和 Pinia store，按租户、Domain、Code 缓存；切换租户或重新登录时清空缓存。
3. 选项值必须使用稳定 code，显示名称仅用于界面。历史单据继续按快照显示旧名称，不根据最新字典改写。
4. 首批必须接入：全部假别、费用类别、采购类别和金额档、印章及文件类别、合同类型、附件类型、常用审批意见。
5. 对当前前后端名称不一致的数据增加兼容迁移或统一 code 映射，禁止继续以中文名称作为接口枚举值。

#### R-B2：差旅标准闭环

1. 创建/编辑页显示员工职级、目的地城市等级、每日住宿上限、每日餐补、标准交通方式、测算天数/人数和允许预算。
2. 超标时保留用户已填内容并定位到“超标原因”，填写后允许按产品规则继续提交审批；详情页和审批页均显示超标金额、原因和冻结的配置版本。
3. 当前实现以住宿和餐补乘以天数、人数计算总上限，但同时保存了交通标准。worker 必须先在 PRD/API 文档明确交通费的计算口径，再修改服务，不能只在前端补字段。

#### R-B3：调休额度账本

调休不是单一年度余额。每次授予必须形成带到期日的 grant，请假保存/提交时按最早到期优先冻结，审批通过后核销，驳回、撤回或取消后原 grant 释放；到期额度不得继续使用，也不得让旧 grant 的已用天数再次扣减新 grant。余额接口需要返回可用总额和近期到期明细，便于前端提示。
