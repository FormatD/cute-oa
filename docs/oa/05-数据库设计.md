# OA V1.0 数据库设计（逻辑模型）

## 1. 通用字段

业务表默认包含：`id`、`tenant_id`、`created_at`、`created_by`、`updated_at`、`updated_by`、`deleted_at`、`version`。所有查询必须带 `tenant_id`，更新使用 `version` 做乐观锁。

## 2. 核心实体

| 领域 | 表/实体 | 关键关系 |
|---|---|---|
| 租户 | tenant、tenant_config | 一个租户拥有多个用户和组织 |
| 身份 | oa_user、user_account、security_role、user_role、role_permission、role_data_scope、auth_session | 用户属于租户，可有多个角色并由角色聚合权限/业务数据范围；登录会话绑定用户 |
| 组织 | department、position、oa_user.position_id；规划 org_unit、user_org、user_position | 当前部门树、单一主岗位和直属上级已持久化，兼任组织/多岗位后续扩展 |
| 流程 | process_definition、process_node、process_rule | 定义按版本发布 |
| 运行 | flow_instance、flow_task、flow_action | 实例关联业务类型和业务 ID |
| 表单 | form_definition、form_version、form_field | 表单版本不可覆盖历史 |
| 文件 | file_object、file_version、file_relation | 文件与业务对象关联 |
| 消息 | notification、notification_delivery、notification_read | 站内信和渠道投递 |
| 公告 | announcement、announcement_read | 公告版本状态与用户阅读确认 |
| 人事 | personnel_profile、personnel_event | 档案与用户一对一；生命周期事件只追加 |
| 考勤 | attendance_shift、attendance_record、attendance_appeal、attendance_month_lock | 班次规则、员工每日记录、异常申诉审核和月度封账 |
| 劳动合同 | employment_contract、employment_contract_event、contract_alert_ack、contract_alert_delivery | 合同版本链、只追加事件、预警确认与幂等派发 |
| 审计 | audit_log、operation_event | 记录关键读写和状态变化 |
| 业务 | leave_request、travel_request、expense_claim、purchase_request、employment_contract | 审批业务关联流程实例；合同使用独立状态机和续签链 |

## 3. 业务单据共性

每个单据至少包含：业务编号、申请人、所属部门、业务字段、当前状态、当前流程实例 ID、提交时间、完成时间和版本号。明细项使用独立子表，不把可查询字段全部塞进 JSON。

当前轻量流程实现使用 `process_definition` 保存编码、业务类型、版本、发布状态和 `priority`，`process_rule` 保存按指标递增的条件上限，`process_node` 保存规则命中后的顺序审批人解析键。`process_scope` 以 `scope_type + value` 保存部门和请假类型适用条件；同一定义内条件唯一，定义删除时级联删除范围。请假、报销与出差单保存流程定义外键、编码和版本快照，流程定义只归档不删除，以保证历史可追溯。

`flow_delegation` 保存委托人、代办人、业务范围、起止时间、状态和取消时间。请假与报销任务通过可空外键关联委托记录，并快照原审批人 ID/姓名；委托记录只取消不删除，确保代办轨迹可解释。

`flow_instance` 已作为独立运行实体落地：每次提交记录业务类型、业务 ID/编号、申请人、流程定义版本、提交次数、运行状态及起止时间；请假和报销单通过 `current_flow_instance_id` 指向当前实例。驳回后修改重提会新增递增的实例，旧实例不覆盖。`flow_action` 以只追加方式保存提交、同意、驳回、转办和撤回动作，包含任务/节点、操作者、意见和转办双方快照；即使当前任务被重建，历史动作仍可追溯。任务通过 `flow_instance_id` 关联其所属实例。

`flow_copy_recipient` 保存请假/报销/出差业务 ID、业务编号、发起人与标题快照、抄送人、流程结果、可阅读时间和已阅时间。同一业务与同一抄送人只能有一条记录；草稿和审批中记录的 `available_at` 为空，不提供数据权限。流程审批完成或申请撤回时一次性激活，抄送人由此获得关联单据及附件的只读权限；已阅状态不与普通站内通知混用。

`oa_user` 保存姓名、部门、直属上级、社会工龄、状态、乐观锁版本和创建/更新时间；`user_account` 一对一保存随机盐、密码哈希、迭代次数、连续失败次数、锁定截止时间和密码变更时间。`security_role`、`user_role`、`role_permission` 分别保存角色、用户多角色关系和操作权限；密码、盐和哈希永不写入审计摘要。演示租户启动时只插入缺失的部门、角色、权限、用户和账号，不执行全库重置。

`department` 保存不可变编码、租户、名称、父部门、同级排序、系统预置标记、乐观锁版本及创建/更新时间。父部门使用自引用外键并禁止数据库级联删除；应用层禁止循环层级、超过 8 层、删除系统部门、删除有下级的部门以及删除仍被 `oa_user.department_id` 引用的部门。部门层级变化会批量撤销租户有效会话，避免旧令牌继续沿用过期组织范围。

`position` 保存不可变编码、名称、所属部门、排序、启停状态、系统预置标记、乐观锁版本及时间戳。`oa_user.position_id` 为可空限制删除外键；分配时应用层校验岗位为 ACTIVE 且与用户主部门一致。已被用户引用的岗位不可移动到其他部门、停用或删除。V1.0 每个用户只支持一个主岗位，多岗位与兼任组织后续通过关系表扩展。

`announcement` 保存标题、正文、`DRAFT/PUBLISHED/WITHDRAWN` 状态、乐观锁版本、创建/发布/撤回操作者与时间以及可选失效时间。草稿可编辑，发布后内容不可覆盖，只能撤回。`announcement_read` 以 `announcement_id + user_id` 唯一保存员工确认已读时间；重复确认不产生重复记录。普通员工列表仅查询已发布且未过期公告，按发布时间倒序。

`auth_session` 保存会话 ID、用户、刷新令牌 SHA-256 摘要、创建/最近使用/过期/撤销时间、撤销原因、User-Agent 和网络地址；不保存刷新令牌明文。刷新时以旧摘要为条件原子更新新摘要，旧令牌重复使用会撤销对应会话。密码重置、账号状态变化和安全角色变化批量撤销用户的有效会话。

`role_data_scope` 以 `role_code + resource_type` 为主键，当前资源类型为 `Leave`、`Expense`、`Travel`、`Personnel`、`Attendance`、`Contract`，范围值为 `SELF`、`DEPARTMENT`、`DEPARTMENT_AND_CHILDREN`、`COMPANY`。系统和自定义角色每个资源类型都必须有一条记录；启动补种只填缺失记录，不覆盖管理员配置。

`personnel_profile` 与 `oa_user` 一对一，保存租户唯一工号、工作联系方式、办公地点、用工类型、人事状态、入职/试用/转正/累计工作起始/离职日期、离职原因和乐观版本。部门、岗位、直属上级和账号状态仍以 `oa_user` 为唯一来源，避免双写两套组织主数据。`personnel_event` 以只追加方式保存入档、档案更新、调岗、转正、发起离职和离职办结事件，包含生效日期、摘要、操作者和变更后快照。

`attendance_shift` 保存租户班次编码、名称、上下班时间、休息分钟、迟到/早退宽限、默认/启停状态和乐观版本。`attendance_record` 以 `tenant_id + user_id + work_date` 唯一，保存员工/部门和班次快照、原始上下班打卡、当前与原始异常、工作及异常分钟、来源和版本；申诉通过只把当前状态改为 `CORRECTED`，不覆盖原始异常。`attendance_appeal` 保存原因、附件 JSON、提交人、审核人、意见和状态，记录不物理删除。`attendance_month_lock` 以租户和月份唯一保存封账状态、乐观版本、封账/解封人、时间和原因；每次状态变化同时写审计日志。

`employment_contract` 保存合同编号、员工/组织/岗位快照、合同类型、签订/起止/试用日期、附件、状态、续签来源、终止登记和乐观版本。`employment_contract_event` 只追加变更后快照；`contract_alert_ack` 以合同和阈值唯一保存人工确认；`contract_alert_delivery` 以合同、接收人和阈值唯一，保证后台任务重复执行或应用重启不会重复发送同档站内通知。有效合同日期重叠由应用事务在激活/续签时校验，生产高并发场景仍应通过串行化操作或数据库排他约束进一步加固。

`travel_request` 保存申请人/部门快照、事由、首尾日期、日历天数、预估预算、多段行程 JSON、同行人 ID JSON、附件、流程版本和当前实例；结构化的日期、状态、预算和申请人用于筛选与权限。`travel_task` 保存出差当前实例任务。`expense_claim.travel_request_id` 为可空限制删除外键，一个出差可关联多张报销单；应用层只允许申请人关联本人已批准出差。

允许使用 JSON 的范围：可配置表单扩展字段、流程快照、第三方原始响应；核心筛选、统计和权限字段必须结构化存储。

## 4. 约束与索引

- `tenant_id + business_no` 唯一。
- `tenant_id + status + created_at` 用于业务列表。
- `tenant_id + assignee_id + task_status` 用于待办列表。
- `tenant_id + business_type + business_id + attempt` 唯一，保证同一单据的提交次数不重复。
- `flow_instance_id + occurred_at` 用于按时间读取永久流程轨迹。
- `tenant_id + business_type + business_id + recipient_id` 唯一，避免重复抄送。
- `process_definition_id + scope_type + value` 唯一，避免流程范围条件重复。
- `tenant_id + recipient_id + read_at + available_at` 用于“待我阅读”查询和未读统计。
- `tenant_id + applicant_id + created_at` 用于我的申请。
- `tenant_id + department_id + status + name` 用于用户管理筛选；用户列表在数据库按创建时间倒序分页。
- `tenant_id + parent_id + sort_order + name` 用于按父节点稳定读取部门树；部门名称在演示租户内由应用层保持唯一。
- `tenant_id + department_id + status + sort_order + name` 用于按部门读取启用岗位；`tenant_id + department_id + name` 唯一。
- `tenant_id + status + published_at` 用于公告发布列表；`announcement_id + user_id` 唯一保证阅读确认幂等。
- `user_id + role_code` 和 `role_code + permission_code` 分别唯一，避免重复授权。
- `refresh_token_hash` 唯一；`user_id + revoked_at + expires_at` 支持用户设备列表和有效会话校验。
- `role_code + resource_type` 唯一，角色删除时级联删除数据范围。
- `tenant_id + employee_number` 唯一；`tenant_id + personnel_status + hire_date` 支持花名册筛选排序。
- `tenant_id + user_id + effective_date + created_at` 支持员工生命周期倒序查询。
- `tenant_id + user_id + work_date` 保证员工每日考勤唯一；`tenant_id + work_date + status + user_id` 支持月度异常列表。
- `tenant_id + code` 保证班次编码唯一；`tenant_id + status + submitted_at` 支持待审核考勤申诉查询。
- `tenant_id + month` 保证每月唯一封账状态；`tenant_id + is_locked + month` 支持快速判断历史月份是否可变更。
- 所有外键逻辑校验租户一致性，禁止跨租户关联。
- 审计表按月分区或归档，避免长期增长影响业务查询。
- 文件元数据与对象存储分离，数据库不保存大文件二进制。

## 5. 关键事务

提交单据事务：校验权限和状态 → 保存单据 → 生成业务编号 → 创建流程实例 → 解析首节点 → 创建任务 → 写事件/审计 → 提交事务。事务失败时不得留下“已提交但无待办”的半成品。
