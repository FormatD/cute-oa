# 人事档案与员工生命周期 PRD

## 1. 产品目标

人事档案模块在现有账号、部门、岗位和直属上级之上建立统一员工主数据，支持花名册查询、个人档案、入职、试用、转正、调岗和离职状态记录，为年假、考勤、劳动合同、招聘入职和人员统计提供可信来源。

V1.0 不保存身份证号、家庭住址、银行卡、健康信息等高敏感个人信息；这些字段需要字段级加密、脱敏、访问审计和更严格授权后再扩展。当前模块只使用模拟数据。

生产账号和人事档案采用一次建档：系统管理员新建用户时必须同时填写真实工号、入职日期、用工类型和人事状态，可填写累计工作起始日；用户、临时登录凭据、角色、档案、初始事件和审计一次提交。临时密码只允许进入短期单次改密挑战，不签发业务会话；用户设置正式强密码后才继续 MFA 或进入系统。花名册查询不得隐式创建档案或根据账号 ID、当前日期和人工工龄猜测人事事实。开发演示种子账号保留统一演示密码和直接登录，生产启动会拒绝任何缺少档案的账号，历史账号必须先通过受控迁移补录。

历史补录使用离线工具，不开放绕过启动门禁的匿名或弱授权接口。导入默认仅预检，要求具备 `PERSONNEL_MANAGE` 的有效操作人，禁止覆盖已有档案；显式应用时整批提交档案、员工状态/工龄、初始事件和审计，任一行失败整批不写。输入模板见 `deploy/templates/personnel-profile-import.example.json`。

## 2. 角色与数据权限

| 角色 | 能力 |
|---|---|
| 员工 | 查看本人档案和本人生命周期记录 |
| 直属及上级主管 | 查看管理链下属档案，不可编辑 |
| HR/行政 | 查看并受控导出全公司花名册；编辑档案、组织关系和员工状态 |
| 系统管理员 | 与 HR 相同，并可维护角色权限 |

新增权限：

- `PERSONNEL_SCOPE_VIEW`：按数据范围查看员工档案；
- `PERSONNEL_EXPORT`：按人事数据范围和当前筛选导出花名册，必须与范围查看权限同时授予；
- `PERSONNEL_MANAGE`：编辑档案、组织关系和员工状态。

人事档案数据范围支持仅本人、本部门、本部门及下级部门、全公司。管理链查看作为直属管理职责单独授权，不依赖角色数据范围。所有服务端接口重新校验查看或编辑权限。

## 3. 页面

### 3.1 花名册 `/hr/employees`

- 服务端分页、默认按入职日期倒序；
- 权限范围、部门、状态、用工类型和关键字均在 PostgreSQL 过滤，数据库完成计数、排序和 `LIMIT/OFFSET`；当前页通过联接一次取得部门、岗位和上级名称，不得逐员工查询；
- 筛选：关键字、部门、在职状态、用工类型；
- 列：工号、姓名、部门、岗位、直属上级、入职日期、用工类型、人事状态；
- 普通员工只返回本人，上级返回管理链下属和本人，HR 按配置范围返回员工；
- 点击进入独立档案详情。
- 具备 `PERSONNEL_EXPORT` 时显示“导出当前结果”；导出复用页面筛选和服务端数据范围，按相同顺序生成 UTF-8 BOM CSV。同步最多 10000 行，超限提示缩小筛选；字段防护电子表格公式注入，成功记录操作者、筛选摘要和行数审计。

### 3.2 档案详情 `/hr/employees/:id`

展示：

- 基础身份：工号、姓名、工作邮箱、工作电话；
- 任职信息：部门、主岗位、直属上级、办公地点、用工类型；
- 生命周期：入职日期、试用期结束日期、转正日期、人事状态、离职日期和离职原因；
- 工龄信息：累计工作起始日期、系统计算的社会工龄；
- 只追加的变更历史：事件类型、生效日期、摘要、操作人和操作时间。

有 `PERSONNEL_MANAGE` 权限时可进入编辑模式。

## 4. 字段与规则

| 字段 | 规则 |
|---|---|
| 工号 | 必填，2–32 位字母、数字、横线；租户内唯一；创建后不可修改 |
| 工作邮箱 | 可选，最多 128 字符，填写时必须为基本邮箱格式 |
| 工作电话 | 可选，5–32 字符，仅允许数字、空格、`+ - ( )` |
| 办公地点 | 可选，最多 100 字符 |
| 用工类型 | `FULL_TIME`、`PART_TIME`、`INTERN`、`CONTRACTOR` |
| 人事状态 | `PROBATION`、`ACTIVE`、`OFFBOARDING`、`TERMINATED` |
| 入职日期 | 必填，不晚于当前日期后 90 天 |
| 试用期结束日期 | 仅试用员工需要；不得早于入职日期 |
| 转正日期 | 可选，不得早于入职日期；填写后状态不能仍为试用 |
| 累计工作起始日期 | 可选，不晚于当前日期；用于计算法定年假社会工龄 |
| 离职日期 | 进入离职办理或离职办结时必填，作为离职清单的计划生效日期；不早于入职日期 |
| 离职原因 | 进入离职办理或离职办结时必填，1–500 字符 |

组织关系继续使用现有部门、岗位、直属上级约束：岗位必须属于所选部门，上级必须为有效员工，管理链不能形成循环。

## 5. 生命周期规则

```text
PROBATION ──转正──> ACTIVE ──发起离职──> OFFBOARDING ──办结──> TERMINATED
```

- 允许 HR 修正历史状态，但必须填写变更说明并写生命周期事件；
- `OFFBOARDING` 必须填写计划离职日期和原因，系统按计划离职日期自动生成标准离职清单；
- `TERMINATED` 只能从 `OFFBOARDING` 进入，且必须完成与本次计划离职日期完全一致的离职清单；任意历史其他日期的完成记录不得放行；
- `TERMINATED` 会同步停用登录账号并撤销所有会话；历史业务、流程、审计和档案不可删除；
- 从离职状态恢复为在职状态会重新启用账号，但不恢复旧会话；
- 部门、岗位或直属上级变化写 `TRANSFER` 事件；
- 试用转在职写 `REGULARIZED`；进入离职办理写 `OFFBOARDING_STARTED`；办结写 `TERMINATED`；其他修改写 `PROFILE_UPDATED`；
- 事件为只追加记录，不能编辑或删除。

## 6. 社会工龄与年假衔接

- 社会工龄按“当前日期 − 累计工作起始日期”的完整年数计算；
- 人事档案更新累计工作起始日期时，同步更新现有用户表中的兼容社会工龄字段；
- 请假模块优先读取精确累计工作起始日期计算完整社会工龄；连续工作满 1/10/20 年分别采用 5/10/15 天法定基线；
- 当年新入职且已满足连续工作条件时，按本单位剩余日历天数占全年比例向下取整；余额按自然年度隔离，HR 可在法定基线上按版本进行 0.5 天粒度调整并写审计；
- 未维护累计工作起始日期时，保留当前人工维护的社会工龄值。

## 7. API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/hr/employees` | 权限化花名册筛选与分页 |
| GET | `/api/v1/hr/employees/export` | 独立导出权限；按当前范围与筛选导出最多 10000 行安全 CSV |
| GET | `/api/v1/hr/employees/me` | 当前员工档案 |
| GET | `/api/v1/hr/employees/{id}` | 档案详情和事件历史 |
| PUT | `/api/v1/hr/employees/{id}` | 编辑档案和组织关系，携带版本号及变更说明 |
| POST | `/api/v1/admin/users` | 创建账号并原子建立初始人事档案；生产必须显式提供建档字段 |
| POST | `/api/v1/auth/password/change-initial` | 使用短期单次挑战修改临时密码，完成后继续 MFA 或登录 |

更新接口必须支持幂等键和版本并发控制。客户端版本用于提前提示；`personnel_profile.Version` 和 `oa_user.Version` 同时作为数据库并发条件，跨应用实例发生陈旧写入时返回 `CONCURRENCY_001`，档案、员工主数据、事件、审计和通知整体回滚。员工档案不存在时返回 `PERSONNEL_004` 并要求受控补录，读取接口不得创建或重置档案。

## 8. 错误码

| 错误码 | 含义 |
|---|---|
| `PERSONNEL_001` | 档案字段不合法 |
| `PERSONNEL_002` | 工号重复 |
| `PERSONNEL_003` | 生命周期日期或状态不一致 |
| `PERSONNEL_004` | 账号缺少人事档案，需受控补录 |
| `PERSONNEL_EXPORT_001` | 同步导出超过配置行数上限 |
| `PERSONNEL_CASE_003` | 未进入离职办理或本次计划离职清单未完成 |
| `AUTH_002` | 无查看或编辑权限 |
| `CONCURRENCY_001` | 档案版本冲突 |

## 9. 验收用例

1. 普通员工只能在花名册看到本人并查看本人档案。
2. 部门负责人可查看管理链内下属但不能编辑。
3. HR 可查看全公司并编辑档案；普通员工调用更新接口被拒绝。
4. 工号租户内重复、无效邮箱/电话、错误日期组合均被拒绝。
5. 调整部门时岗位不属于目标部门会被拒绝；有效调岗写 `TRANSFER` 事件。
6. 试用员工填写转正日期并改为在职后写 `REGULARIZED` 事件。
7. 进入离职办理必须有计划离职日期和原因，并自动生成同日期离职清单；清单未完成不能办结。
8. 历史其他日期的已完成离职单不能放行本次离职；匹配日期清单完成后账号停用、既有会话失效。
9. 恢复为在职后账号重新启用但旧会话仍不可用。
10. 修改累计工作起始日期后社会工龄按完整年数更新，并影响后续年假计算。
11. PostgreSQL 重启后档案和只追加事件完整保留；应用重启不覆盖 HR 修改。
12. 花名册按入职日期倒序分页，筛选和关键字查询正确。
13. 所有编辑、状态变化和组织变化写审计日志。
14. 两个独立应用实例同时编辑同一档案或员工主数据时只有首个提交成功，后续陈旧提交返回 `CONCURRENCY_001` 且不覆盖首个结果。
15. 两个独立应用实例同时处理同一员工办理任务或办理单时只有首个提交成功，通知、审计和任务状态不重复。
16. 生产创建账号缺少工号、入职日期、用工类型或人事状态时整体拒绝；成功时账号、角色、档案、初始事件和审计同时存在。
17. 连续读取花名册和档案不会增加或修改 `personnel_profile`、`personnel_event`；生产库存在缺档账号时启动失败并提示受控补录。
18. 离线补录默认预检零写入；一行合法、一行非法时整批零写入；修正后档案、员工状态/工龄、初始事件和审计同时提交，重复执行不能覆盖已有档案。
19. 至少 250 人花名册按关键字和部门查询第 3 页时只执行计数与当前页两条 SQL，返回 25 人且顺序正确；列表行数增加不能产生逐员工关联查询，`%`、`_` 按普通关键字字符处理。
20. 新建、管理员重置和生产引导账号标记为临时密码；临时密码登录不创建会话，弱正式密码、复用临时密码、过期或旧挑战均被拒绝；最新挑战只能消费一次，成功写审计并继续 MFA 或签发会话。开发演示种子账号仍可直接使用统一演示密码。
21. 普通员工和仅可查看下属的负责人不能导出；HR 按当前筛选和全公司范围导出。CSV 包含 UTF-8 BOM，电话等前导 `+` 值和公式字符安全转义，成功写 `PERSONNEL_ROSTER_EXPORTED` 审计；超过上限返回 `PERSONNEL_EXPORT_001`。

## 10. 后续 HR 路线

1. 考勤班次、打卡导入、异常申诉与月度汇总；
2. 劳动合同台账、试用/续签/到期提醒；
3. 招聘录用与入职办理单自动衔接；
4. 招聘职位、候选人和录用入职转换；
5. 薪酬数据只做受控接口集成，不在通用 OA 中明文存储。
