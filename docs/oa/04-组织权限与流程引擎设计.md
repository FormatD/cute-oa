# 组织权限与流程引擎设计

## 1. 组织模型

```text
租户
 └── 组织单元（公司/部门/团队）
      └── 岗位
用户 ── 主部门/兼任部门/岗位
用户 ── 角色 ── 权限
```

用户至少具备：姓名、工号、手机号、邮箱、主部门、岗位、直属上级、状态、入离职日期。离职用户不可发起新业务，但历史数据和审批轨迹必须保留。

当前部门树以公司根节点为起点，最多支持 8 层。部门编码创建后不可修改，编码和名称在租户内唯一；系统预置部门可调整名称、上级和排序但不可删除。移动部门时禁止以自身或下级部门为父节点，并按整个子树校验层级上限。存在下级部门或在职/停用用户引用时不允许删除。部门更新使用乐观版本号，层级变化会撤销演示租户全部有效会话，使数据范围和经理链在下一次登录时重新计算。

直属上级关系独立于部门负责人角色，禁止用户管理操作形成直接或间接经理循环。部门与上级调整不改写历史单据中的申请部门和审批人快照。

岗位隶属于一个部门，编码创建后不可修改，同一部门内名称唯一。岗位只表达组织职责，不聚合任何操作权限或数据范围；安全角色只表达授权，不作为岗位。用户当前可选择一个主岗位，岗位必须启用且属于用户主部门。已分配岗位不能跨部门移动、停用或删除；系统预置岗位不可删除。岗位与用户岗位变化均写审计，用户岗位变化撤销该用户的有效会话以刷新通讯录资料。

## 2. 权限模型

权限分为菜单、操作、API、数据和字段权限。最终判定必须同时满足“租户有效 + 用户有效 + 角色授权 + 资源范围允许 + 当前状态允许”。

数据范围建议支持：本人、所属部门、部门及下属、指定范围、全公司。前端隐藏按钮不能代替服务端校验。

### 2.1 已落地的角色与权限

| 权限码 | 用途 | 默认角色 |
|---|---|---|
| `USER_MANAGE` | 查询、新建、编辑、停用用户及重置密码 | 系统管理员 |
| `ORG_MANAGE` | 查询、新建、编辑、移动和删除部门 | 系统管理员 |
| `ANNOUNCEMENT_MANAGE` | 创建、编辑、发布和撤回公司公告 | HR/行政、系统管理员 |
| `PROCESS_MANAGE` | 维护和发布流程定义 | 系统管理员 |
| `AUDIT_VIEW` | 查询审计日志 | 系统管理员 |
| `CALENDAR_MANAGE` | 维护企业工作日历 | HR/行政、系统管理员 |
| `EXPENSE_PAY` | 登记报销付款 | 财务专员、财务经理、系统管理员 |
| `LEAVE_SCOPE_VIEW` | 启用角色的跨用户请假范围 | 系统管理员及按需配置角色 |
| `EXPENSE_SCOPE_VIEW` | 启用角色的跨用户报销范围 | 财务、系统管理员及按需配置角色 |
| `TRAVEL_SCOPE_VIEW` | 启用角色的跨用户出差范围 | 系统管理员及按需配置角色 |
| `PERSONNEL_SCOPE_VIEW` | 启用角色的跨用户人事档案范围 | HR/行政、系统管理员及按需配置角色 |
| `PERSONNEL_MANAGE` | 编辑人事档案、组织关系和员工状态 | HR/行政、系统管理员 |
| `ATTENDANCE_SCOPE_VIEW` | 启用角色的跨用户考勤范围 | HR/行政、系统管理员及按需配置角色 |
| `ATTENDANCE_MANAGE` | 维护班次、导入考勤和审核异常申诉 | HR/行政、系统管理员 |
| `CONTRACT_SCOPE_VIEW` | 启用角色的跨用户劳动合同范围 | HR/行政、系统管理员及按需配置角色 |
| `CONTRACT_MANAGE` | 创建、激活、续签、终止合同并处理预警 | HR/行政、系统管理员 |
| `EXPENSE_ALL_VIEW` | 查看全公司报销 | 财务专员、财务经理、系统管理员 |

用户可拥有多个角色，权限取所有角色权限的并集，首个角色作为展示和兼容用主角色。系统管理员可新增自定义角色、编辑角色名称和上述操作权限；系统预置角色不可删除，自定义角色只有在未分配用户时可删除。角色编码创建后不可修改，编码和名称在租户内唯一。

用户管理使用乐观版本号避免并发覆盖；管理员不能停用自己，也不能通过用户分配或角色定义移除自身最后一份 `USER_MANAGE` 权限。用户角色、账号状态或角色权限集合变化会撤销受影响用户的有效登录会话，但不改写历史单据、流程实例和审批人快照。

### 2.2 已落地的数据范围

角色按业务类型分别配置请假、报销、出差、人事档案、考勤和劳动合同数据范围：`SELF`（仅本人）、`DEPARTMENT`（本部门）、`DEPARTMENT_AND_CHILDREN`（本部门及全部下级部门）、`COMPANY`（全公司）。跨用户范围必须同时具备对应的范围查看权限；`PERSONNEL_MANAGE`、`ATTENDANCE_MANAGE`、`CONTRACT_MANAGE` 必须分别与对应范围查看权限配对。多角色按同一业务下最宽的合格范围聚合，不能把一个角色的范围与另一个角色不相关的权限拼接放大。

直属上级查看下级及其间接下级属于人事档案、考勤等业务的组织关系授权；劳动合同属于敏感资源，明确例外，管理链不会自动放行合同正文与附件。财务专员和财务经理默认仅有全公司报销范围，不能借此查看全公司请假、人事、考勤或合同；系统管理员对当前六类资源均为全公司。范围变化会撤销该角色所有用户的有效会话，下一次登录按新范围重新计算。

## 3. 流程定义

流程定义包含：编码、名称、业务类型、版本、状态、适用组织、触发条件、节点列表、路由规则和发布人。已发布版本不可直接修改，只能复制生成新版本。

节点类型：发起、审批、抄送、条件、并行、结束、自动动作。审批人解析支持直属上级、部门负责人、岗位、指定用户、角色和业务字段指定人。

### 3.1 适用范围与匹配顺序

- 适用部门为空表示全公司；指定部门时包含该部门及全部下级部门。
- 请假流程的适用假别为空表示全部假别；可指定年假、事假、病假或调休。报销流程不得设置假别条件。
- 新单据提交时只匹配相同业务类型（Leave、Expense、Travel）的已发布流程，依次按优先级降序、条件具体度降序、版本降序和发布时间降序选择。
- 条件具体度按“已指定部门”“已指定假别”两个维度计数；例如同时限定研发部和病假的流程比仅限定研发部的流程更具体。
- 不同编码的已发布流程如果业务类型、优先级和具体度相同且适用范围相交，发布时返回 `FLOW_003`，避免运行时选择不确定。
- 同编码发布新版本时先归档旧发布版本；既有单据和流程实例继续绑定原版本，不重新匹配。

## 4. 流程任务规则

| 能力 | V1.0要求 |
|---|---|
| 会签 | 全部通过、任一通过、按比例通过可配置 |
| 驳回 | 驳回到发起人或指定节点，保留原轨迹 |
| 撤回 | 仅在下一节点未处理前允许，受业务规则限制 |
| 转办 | 记录原审批人、接收人和原因 |
| 委托 | 按时间范围和业务类型生效，委托关系可审计 |
| 加签 | 加签人完成后回到原任务或按配置结束 |
| 超时 | 提醒、升级、自动转交均需开关和日志 |

## 5. 通用状态机

```text
DRAFT → SUBMITTED → APPROVING → APPROVED → COMPLETED
                       ├────────→ REJECTED → DRAFT
                       └────────→ WITHDRAWN
```

业务模块可增加中间状态，但不得绕过流程直接修改最终状态。状态迁移由服务端校验，重复迁移返回明确错误。

## 6. 报销状态示例

| 状态 | 允许操作 |
|---|---|
| DRAFT | 编辑、删除、提交 |
| APPROVING | 撤回（满足条件）、审批人审批 |
| REJECTED | 编辑、删除、重新提交 |
| APPROVED | 财务确认、付款 |
| PAYING | 记录付款、撤销付款（需财务权限） |
| COMPLETED | 查询、导出 |

金额路由示例：`≤1000` 部门负责人→财务；`1000~5000` 增加财务经理；`>5000` 增加总经理。阈值配置化，规则变更只影响新提交单据。
